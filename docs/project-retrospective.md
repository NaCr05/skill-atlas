## 状态口径

- **已实现且验证**：在当前源码中存在，并由本轮实际检查、隔离夹具测试或当前提交的 GitHub CI 证明。
- **已实现但未验证**：实现和测试入口已经存在，但本轮没有在真实外部服务、真实安装包或真实用户数据上完成验证。
- **计划中或未完成**：尚无完整实现，或当前发布流程尚未把实现交付给普通用户。

## 项目目标与最终成果

Skill Atlas 的目标是为 Windows 上的 Codex 用户提供一个本地、可审查的 Skill 控制台：扫描已安装 Skill，解释用途与调用规则，按任务推荐并生成调用 Prompt，同时通过“先审查、后确认”的流程管理安装、更新、停用、回收、恢复和清理。项目坚持以磁盘上的 Skill 文件为事实来源，不建立云端账户或数据库，也不让可选 AI 自动取得文件写入权限。

当前成果已经从“Skill 清单”扩展为本地生命周期工作台：包含清单与图谱、双语界面、确定性 Prompt、市场发现、安装审查、来源追踪、安全更新、停用与恢复、回收站、恢复中心、操作中心、来源策略、数据导入导出及显式触发的 AI 辅助。核心本地流程在当前 `main` 上通过了类型检查、代码规范、129 项单元/集成测试、生产构建和 24 项 Chromium 端到端测试。

## 关键技术决策

| 决策 | 原因 | 结果与代价 |
| --- | --- | --- |
| 本地单进程、仅绑定 `127.0.0.1` | 降低部署和隐私成本，避免把个人 Skill 暴露为网络服务 | 适合个人 Windows 工作站；不支持多人、远程或服务器部署。 |
| 文件系统是事实来源 | Codex 实际使用磁盘上的 `SKILL.md` 和配套目录 | 不会把推断元数据写回 Skill；扫描和指纹计算成为关键可靠性边界。 |
| 摘要与完整正文分开加载 | 避免清单载荷随全部 Skill 正文线性膨胀 | 清单、图谱和推荐只用摘要；详情页按需读取完整说明。 |
| 确定性基础能力，AI 仅作显式增强 | 无密钥也必须可用，且模型不应悄然产生费用或授权写入 | 每个 AI 流程都有独立按钮、一次请求、严格结构和本地回退；质量上限受本地规则与所选模型共同影响。 |
| 审查计划短期、限量、一次性 | 防止旧审查被重复利用或在目标变化后继续执行 | 安装、更新、删除和清理必须重新确认；流程更安全，但点击步骤更多。 |
| 完整目录指纹、私有暂存、原子替换和回滚 | 更新与删除涉及不可逆风险，不能依赖“尽量成功” | 能发现本地漂移并在失败后恢复；Windows 文件占用和多进程并发仍是边界。 |
| 外部来源默认不可信 | Skill 可携带脚本、代理说明和诱导性文本 | 检查文件树、来源、许可证和风险，但不执行下载脚本；自然语言恶意指令仍需人工判断。 |
| 浏览器本地状态与服务端生命周期记录分离 | 收藏、备注和历史不应改动 Skill；事务证据必须在文件系统上可靠保存 | 个人偏好易于使用和导出，但浏览器备注未加密；事务日志和指纹才是恢复依据。 |
| CMD/PowerShell 薄包装，共用一个启动器实现 | 避免两个 Windows 入口长期漂移 | 统一了环境检查、端口选择和浏览器打开；仍要求本机已有 Node.js，源码版首次使用需安装依赖。 |

更完整的约束见 [架构说明](architecture.md)、[安全模型](security-model.md)、[Skill 生命周期](skill-lifecycle.md) 和 [AI 辅助边界](ai-assistance.md)。

## 做得好的地方

1. **把安全约束变成了可测试的工程边界。** 本地请求校验、真实路径约束、一次性审查计划、内容指纹、事务日志、隔离目录和回滚都不是仅写在文档中，而是进入了核心模块与测试。
2. **离线基础体验完整。** 即使市场或模型不可用，用户仍可扫描、搜索、查看详情、按任务本地推荐并复制确定性 Prompt。
3. **测试环境与真实个人目录隔离。** Playwright 使用专用 `CODEX_HOME` 与夹具目录；生命周期测试没有触碰真实个人 Skill。
4. **关键异步与无障碍风险有专门回归。** “旧请求覆盖新查询”、对话框焦点管理、移动端横向溢出、语言持久化和历史回放都进入了自动化验证。
5. **发布入口面向 Windows 新手。** CMD 与 PowerShell 启动器共享预检逻辑，能够指出目录错误、Node/npm/依赖缺失和端口占用，并在服务就绪后再打开浏览器。
6. **工程知识已经形成复用文档。** `AGENTS.md`、架构、安全、测试、生命周期、AI 和 Windows 分发文档共同说明了产品边界和修改规则。

## 遇到的问题、原因和解决方案

| 问题 | 根因 | 解决方式 | 后续防护 |
| --- | --- | --- | --- |
| 新用户照抄快速启动仍停留在父目录，或在 CMD 中使用 PowerShell 命令 | 早期说明没有清楚区分终端语法和当前目录 | 同时提供 CMD/PowerShell 示例，统一使用可跨终端理解的 `cd`，增加双启动器 | 启动器验证项目目录；启动回归覆盖两个入口和依赖缺失。 |
| 3000 端口被占用或已有 Next.js 实例时启动失败 | 开发服务器默认端口固定，重复启动没有用户友好处理 | 启动器在有限范围内寻找空闲端口，轮询服务就绪后打开正确地址 | 本轮体检实测 3000 被占用时自动选择 3001。 |
| 生命周期能力快速扩张后，写操作规则容易分散 | 安装、更新、删除、停用、归档各自需要审查、审计和恢复 | 抽出统一审查计划、稳定错误码、操作日志、指纹和事务存储边界 | `AGENTS.md` 明确写入规则；单元、集成和端到端测试覆盖主要路径。 |
| README 截图未反映最新界面 | 截图脚本的启动参数与 standalone 运行方式不一致，捕获入口也未稳定落在目标页面 | `bbae7ec` 调整截图配置、等待条件和捕获流程，并更新全部公开截图 | 截图流程只允许夹具目录；更新前先构建并要求人工查看所有产物。 |
| Windows DPAPI 测试在 CI 中偶发超时 | 单项测试的默认超时短于两次外部进程调用的允许时间 | 为该测试设置合理的专用超时 | 当前 `main` 的 GitHub CI 已通过；仍应关注慢速 Windows runner。 |
| 能力与发布版本出现漂移 | 207 个文件的生命周期扩展在 `v0.1.1` 标签之后合并 | `v0.2.0` 已统一版本号、变更记录、源码标签、Release 和安装包 | 后续发布继续把版本对齐与安装包冒烟作为标签门槛。 |
| 生命周期说明中存在前后矛盾的能力表述 | 文档早期边界未随实现统一更新 | 本次收尾以代码、测试、`AGENTS.md` 和当前架构为证据 | 该文件属于本次禁止修改的“其他文档”，需在下一次文档修订中单独校正。 |

## 下次应该怎样做

### 继续保持

- 先定义权限和失败恢复，再增加新的写操作。
- 用隔离 `CODEX_HOME`、确定性夹具和稳定错误码覆盖每条生命周期路径。
- 保持“本地默认可用，AI/市场按需增强”的产品原则。
- 每次提交前执行完整门禁，并让公开截图与实际 UI 同步。

### 应该改进

- 把版本、标签、Release、安装包和文档快照作为一个发布事务，而不是分别处理。
- 为真实外部服务建立受控冒烟环境，避免只有模拟测试而没有运营证据。
- 在大功能合并时同步更新所有边界文档，避免同一文档内部出现冲突。
- 为生命周期人工验收保留临时目录演练脚本和可重复清单。

### 应该停止

- 不要把“代码已合并”描述为“普通用户已发布”。
- 不要在未读取完整目录和来源证据时做一键安装或更新。
- 不要让 AI 建议越过确定性阻断、一次性确认或本地权限边界。
- 不要在测试或截图流程中读取真实个人 Skill 目录。
